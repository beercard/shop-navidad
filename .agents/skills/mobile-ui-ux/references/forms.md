# Forms, input, validation, authentication, and data entry

Read this when: building or reviewing any form, sign-in/sign-up, OTP, checkout, settings, search input, multi-step flow, destructive confirmation, or permission request; choosing keyboard types, autofill tokens, validation timing, or select-like controls.

Tags: `[S]` WCAG/NIST standard · `[P-iOS]` `[P-AND]` `[P-WEB]` platform · `[R]` research (sample noted) · `[C]` consensus · `[H]` heuristic · `[L]` legal/policy. Research date 2026-10-06. Core goal: fewer fields, less typing, fewer errors, recoverable mistakes.

## 1. Field design

- **Visible label above every field, always.** Penzo's eye-tracking (2006, desktop, n not stated): label-above needs ~50 ms label-to-input saccades vs ~500 ms for left labels. NN/g, W3C WAI, GOV.UK and web.dev agree. Sentence case, no trailing colon. `[R][S 3.3.2]`
- **Placeholder is never the label.** It disappears, is mistaken for a value, fails contrast (default placeholder colors usually miss 4.5:1) and forces users to delete their input to see it again after an error (Baymard). Use it only for a short format example ("name@example.com") at ≥ 4.5:1. HIG itself says add a separate label. Exceptions: a single standalone search field, in-app chat composer. `[R][P-iOS]`
- Floating labels are a weakly evidenced compromise (NN/g: better than placeholder-as-label, worse than a static label; Baymard "shows promise", no in-depth testing). If Material is the house system: label ≤ 2-3 words, put format/help in persistent supporting text below, ensure the accessible name starts with the visible label (WCAG 2.5.3), floated label ≥ 4.5:1. Material outlined fields suit multi-field forms, filled suit dialogs/short forms. When showing an error include the format rule inside the error text so the hint is not lost (Material replaces helper with error; GOV.UK keeps both). `[R][P-AND]`
- Hints: one short sentence under the label, linked with `aria-describedby`, no links inside hints, stated before the user types (not after an error). `[R]`
- **Required vs optional:** Baymard: 61% of checkouts don't mark both; where only one is marked, 32% skipped required fields. GOV.UK: never asterisks; mark optional with "(optional)". NN/g: asterisk or word "Required". Rule: if ≥ 80% of fields are required, append "(optional)" to the few optional ones; if mixed, mark both in text, not color alone; asterisk ≥ 4.5:1 with a legend. Remove optional fields where possible.
- Single column on phones (≤ 600dp/px); order by the user's mental model: familiarity, priority, dependency, complexity, sensitivity (sensitive last); group with spacing + `<fieldset><legend>` or section headers. Field width communicates expected length for short fields (CVC 4-5ch, postcode 8-10ch, day/month 2, year 4); never constrain email/name/address below full width.
- Character counters only for real limits and never hard-block typing for soft limits (GOV.UK: allow exceeding so users can paste and trim; show the count once near the limit). Hard protocol limits (OTP length, SMS 160) use `maxLength`.
- Min controls: web `input, select, textarea { font-size: max(16px, 1rem); min-height: 48px }` (iOS Safari zooms a focused input under 16px; never disable zoom); native hit area ≥ 44pt / 48dp including icon buttons inside fields. `[P-WEB][S]`

## 2. Reduce fields and typing (order of attack)

Remove the field → infer/prefill → autofill tokens → right keyboard → pick instead of type → scan/capture → accept liberal formats → forgiving validation → undo. (NN/g mobile input checklist, HIG entering data, Baymard.)
- Baymard 2024: average checkout has 11.3 visible fields vs ~8 needed (12.7 in 2019); 89% split first/last name; 75% show Address Line 2; 35% promo field; 24% default to a separate billing address; 84% make account creation part of checkout. Optional fields shown by default make steps 5-30% longer; ~17% abandon over perceived complexity; 18% over forced account creation; average cart abandonment 70.22% across 50 studies. Fields drive usability more than step count. `[R]` (e-commerce data; principle general)
- Cut or defer: separate first/last (use one full-name field), Address Line 2 (behind "Add apartment, suite" link), promo code (behind link), billing address (default same as shipping), account creation (post-purchase), confirm-email, confirm-password, phone unless required for delivery (say why). Justify every field by an immediate use.
- Defaults: prefill what is inferable (locale, country, time zone, "same as shipping") and keep it editable. Never preselect answers to meaningful questions, consent, marketing opt-ins or add-ons. Defer sign-in until value is clear (HIG); request account creation on the confirmation page. `[P-iOS][R][L]`
- Names: one "Full name" field, `autocomplete=name`, no max length below ~100, no regex beyond non-empty; accept any characters (W3C personal-names; GOV.UK). If parts are needed, parse server-side or ask a separate "preferred name".
- Masks: avoid hard keystroke masks (caret/paste/screen-reader trouble). Normalize on input (strip spaces), format display only for chunkable numbers (cards 4-4-4-4) via a display transformation (Compose `OutputTransformation`, Intl formatters), always accept pasted formatted strings. `[R]`
- Device capabilities over typing: camera/scan (iOS Live Text `captureTextFromCamera`, card scan), GPS, contacts, system pickers (no permission needed: Android Photo Picker, iOS pickers).

## 3. Keyboard, input types, autofill

Rules:
- Use `type=email|tel|url|search` where they match. For identifiers (card, OTP, postcode, account number) use `type=text inputmode=numeric` (+ `pattern="[0-9]*"`): `type=number` cannot be dictated in Dragon, drops letters silently, rounds large numbers, changes with scroll wheel (GOV.UK, MDN). `type=number` only for true incrementable quantities. Amounts: `inputmode=decimal`. `inputmode` is a keyboard hint, not validation. `[P-WEB][R]`
- Set the right `autocomplete` token on every field (feeds autofill and password managers; WCAG 1.3.5 AA). Practical set: `name`, `given-name`, `family-name`, `username`, `new-password`, `current-password`, `one-time-code`, `email`, `tel`, `tel-country-code`, `tel-national`, `street-address`, `address-line1/2`, `address-level1/2`, `country` / `country-name`, `postal-code`, `cc-name`, `cc-number`, `cc-exp`, `cc-exp-month/year`, `cc-csc`, `bday`, `bday-day/month/year`, `organization`, `webauthn` suffix for passkeys. Prefix `shipping`/`billing` for two addresses; `section-*` for multiple people. Password managers ignore `autocomplete=off` on login fields; use `off` only for CAPTCHA-like one-offs. Keep `name`/`id` stable across deploys. `[P-WEB][S]`
- Disable "helpful" text services on structured data: `autocapitalize=none`, `autocorrect=off`, `spellcheck=false` (spellcheck can leak data to third parties) for username/email/URL/code/password; names/addresses `autocapitalize=words`, autocorrect off; free text leave defaults. Native: also turn off smart dashes/quotes on IDs. `[P-WEB][R]`
- Return key: fields 1..N-1 `enterkeyhint=next` / `imeAction=Next` / `submitLabel(.next)` **and move focus in code** (Flutter `TextInputAction.next` does not move focus by itself); field N uses `go/done/send/search` and triggers the same validation + submit as the button. iOS number/decimal/phone pads have no Return key: add an accessory "Next/Done" bar (native) or rely on Safari's assistant bar (memory). RN: `onSubmitEditing` is not called on iOS `phone-pad`.

## 4. Keyboard avoidance and dismissal

- Web: the keyboard shrinks the *visual* viewport (Chrome 108+ `interactive-widget=resizes-visual`, matching iOS Safari); fixed bottom bars and 100vh/dvh layouts can be covered (dvh/svh/lvh deliberately ignore the keyboard). Preferred: an in-flow submit button at the end of the form (nothing to avoid). Else `position: sticky; bottom: 0` in the scroll container with safe-area padding; else listen to `visualViewport` resize/scroll and translate the bar; Chrome Android optionally `interactive-widget=resizes-content`. After focus `scrollIntoView({block:'center'})` once the resize settles (memory). Safari/Firefox support for `interactive-widget` unverified.
- Native: Compose `enableEdgeToEdge()` + `Scaffold` + `Modifier.imePadding()` on the scroll container (needs `adjustResize`); SwiftUI ScrollView + `.safeAreaInset(edge: .bottom)` for the CTA, don't `ignoresSafeArea(.keyboard)` unless overlaying; UIKit `keyboardLayoutGuide` (iOS 15+); Flutter keep `resizeToAvoidBottomInset` true and wrap the form in `SingleChildScrollView`; RN `KeyboardAvoidingView` with explicit `behavior` per platform and `keyboardVerticalOffset`. Android: prefer `adjustResize`.
- Dismissal: RN `keyboardShouldPersistTaps="handled"` + `keyboardDismissMode="on-drag"` (iOS `interactive`) so taps on buttons below inputs aren't swallowed; Flutter `keyboardDismissBehavior: onDrag`; SwiftUI `.scrollDismissesKeyboard(.interactively)`.

## 5. Validation

- Evidence: Wroblewski/Etre 2009 (22 participants, 6 forms, lab, desktop): the best inline variant gave +22% success, -22% errors, +31% satisfaction, -42% completion time, -47% fixations, but benefits concentrated in hard fields (username, password); easy fields (name, address) were looked at by only 30-50% and a success tick on name confused people. 17 years old: treat as directional. Baymard: 31% of benchmarked sites have no inline validation; validate on blur or at expected length; remove an error the instant the field becomes valid. Smashing "reward early, punish late": validate valid fields on blur; fields already in error on every keystroke; empty required fields only on submit; flag gross format errors (letters in a digit field) immediately. GOV.UK dissents deliberately: validate on submit only, server-side always, `novalidate`; HIG: validate email on leaving the field, password before leaving. `[R]`
- Rules: easy free text → no inline success state; format errors on blur; empty required on submit. Hidden-rule fields (password, username availability, card, coupon) → live feedback (debounce ~300-500 ms, memory) with specific messages. A field in error → re-validate on each input and clear the error the moment it is valid. Short single-step flows may validate on submit only with an error summary. Web `:user-invalid`/`:user-valid` (Baseline Nov 2023) match only after interaction; `:invalid` matches on load. Flutter `AutovalidateMode.onUserInteraction` validates on every change after first edit (premature errors). Track a `touched` flag per field in RN/SwiftUI.
- **Error message** = what's wrong + what to do, specific per failure type (empty / too short / too long / bad format / invalid characters), adjacent to the field, in text with icon + border (never color alone), never a code, keep the hint visible, preserve input. Baymard: 94% of checkouts don't use adaptive messages. Instruction style for missing ("Enter your first name"), description for constraints ("Name must be 35 characters or less"). `[R][S 3.3.1/3.3.3]`
- **Error summary + focus** (GOV.UK, W3C WAI): after submit show a summary above the main heading (even for one error), move focus to it, link each item to its field, identical text inline, `aria-invalid="true"`, `aria-describedby`, page title prefixed "Error:". Native: focus the first invalid field and announce. Dynamic errors use a polite live region without stealing focus.
- **Preserve input**: never clear the form on failure (exception: password after failed login; OTP). Autosave drafts locally (debounced) on `visibilitychange`/`onPause`/scene background; restore on return; Android process death wipes state (`rememberSaveable`/ViewModel/`SavedStateHandle`); `beforeunload` only while dirty (unreliable on mobile). WCAG 3.3.7 redundant entry. `[S]`

## 6. Specific fields

- **Phone**: `type=tel`, accept any common format, validate leniently (libphonenumber), explain why you need it; for international use a country-code control + national number or E.164 with leading "+"; never enforce a US pattern.
- **Address**: few flexible fields; country first (searchable, default from locale), adapt labels (State/Province/County, ZIP/Postcode) and required-ness (postal code optional in some countries); autofill tokens everywhere with `shipping`/`billing`; lookup is a convenience (GOV.UK UK lookup-first vs web.dev lookup-secondary: choose by audience); don't force a state dropdown. "Country first" is common practice from memory.
- **Email**: single field, trim, suggest on common-domain typos (non-blocking "Did you mean gmail.com?"), verify by link/code, no confirm-email field.
- **Dates**: known/far dates (birthdays) = three numeric text fields (`inputmode=numeric`, widths 2/2/4, `bday-*`, accept month names) or a platform picker with min/max; near/unknown dates (appointments, travel) = calendar picker with unavailable dates disabled and a typed fallback (Material DatePicker `Input` mode; iOS wheels accept keyboard entry; `type=date` is widely available, value always yyyy-mm-dd). No dropdown triples. Error priority: missing → impossible → invalid.
- **Numbers**: stepper for small bounded counts (≤ ~10) with the value visible; sliders only when approximate values are fine (hard to control on touch, thumb hides the label: show the live value above the thumb, step snaps, offer a field for exact entry, ensure keyboard/AT adjustability); precise or large values = text field with currency prefix/suffix outside the input and `Intl.NumberFormat`/`NumberFormatter`.
- **Files/photos**: system picker first (no permission), camera second; state limits up front; specific errors (missing, wrong type, too big, corrupt, password-protected); `accept` is only a hint (validate server-side); `capture` hints camera; Android Photo Picker needs no permissions.
- **Rich text**: avoid on mobile forms; plain textarea (`enterkeyhint=enter`, `send` for chat), autosave drafts.
- **Search input**: `type=search enterkeyhint=search`, recents/suggestions, clear affordance, don't auto-submit each keystroke unless results are cheap.

## 7. Select-like controls (thresholds are heuristics: no study gives numeric cut-offs)

| Options | Use |
|---|---|
| 2 opposing short options | Segmented control (iOS ≤ ~5 segments) or radios |
| 2-4 (up to 5 with vertical room) | Radio buttons stacked vertically (add "None of the above"/"I do not know"; radios can't be unset; never preselect meaningful answers) |
| 5-10 | Native `<select>` / platform picker (opens the OS picker on mobile, avoiding many desktop dropdown problems) |
| 11-15 | Picker with sections or a searchable sheet `[H]` |
| > 15, dynamic, or familiar typing lists (country, airport) | Searchable combobox (type-ahead + full keyboard/AT support) or native picker |
| Small integer | Stepper |
| Immediate-effect setting | Switch; commit-with-Submit choice = checkbox; consent = unchecked checkbox |
GOV.UK calls select "a last resort"; Wroblewski found alternatives to dropdowns performed better (travel class radio, passengers stepper, date picker). Evidence is desktop-era. Never build a custom div select that breaks native pickers/autofill. Switch: iOS switch only inside list rows; label names the feature and what "on" does; optimistic update + undo/failed state (NN/g toggle guidelines). `[R][P-iOS]`

## 8. Multi-step flows

- Field count matters more than step count (Baymard). Split into steps of 3-6 related fields when > 8-10 fields or branching; show "Step 2 of 4"; Back preserves data; autosave per step; finish consequential submissions with a review screen with "Change" links that return to review (GOV.UK check-answers); don't mark submitted until confirmed.
- One-thing-per-page (GOV.UK, complex branching, low-confidence audiences; based on service-team research, not published controlled comparisons) vs single scrolling page or short accordion (Baymard; autofill-friendly checkout; collapse completed steps into editable summaries). Long multi-session transactions: task list with statuses (GOV.UK: Completed, In progress, Not yet started, Cannot start yet, There is a problem). Wizards suit novices and infrequent tasks (NN/g).
- Checkout: top of payment section Apple Pay/Google Pay system buttons (collect shipping/contact in the wallet sheet; show the amount on the submit button), then guest checkout (Baymard: 62% of sites don't make it most prominent), then card form with `cc-*` autofill; ask for an account after order success. Payment Request API is not Baseline.

## 8b. Unsaved changes (leave guard) and save state

- "Dirty" = values differ from the last saved/loaded snapshot, not "a key was pressed"; clear on successful save; never guard a clean form. `[H]`
- Prefer autosave + restorable draft where loss is cheap to avoid (notes, composers, long forms); guard when saving is an explicit consequential commit (edit profile, settings with Save). Do not persist PII or minors' data in drafts unencrypted: scope to the session, clear on logout. `[H]`
- Guard every exit: Back/Up, Close/Cancel, sheet swipe-down or scrim tap, tab switch, route change, deep link; on web tab close/reload. HIG: unsaved changes in a sheet need a confirmation, never a silent discard. `[P-iOS]`
- iOS: block interactive dismissal while dirty (SwiftUI `interactiveDismissDisabled(hasChanges)`; UIKit `isModalInPresentation` + `presentationControllerDidAttemptToDismiss`, verify). Android: `OnBackPressedCallback`/`PredictiveBackHandler` enabled only while dirty. Flutter `PopScope`; React Navigation `beforeRemove` (verify). Web: `beforeunload` only while dirty and removed after save (generic dialog, needs prior interaction, unreliable on mobile), autosave on `visibilitychange`/`pagehide`, router navigation blocker for SPA routes.
- Dialog: "Discard changes?" or "Save changes to 'Draft'?"; [Keep editing] (default, safe) [Discard changes] [Save]; max 3; Escape/Back = Keep editing; focus returns to the field that had it. Save failure: stay, keep dirty, show the error.
- Save state: explicit save button idle → "Saving…" (fixed width) → "Saved" (~1.5 s) or inline "Couldn't save. Try again." Autosave: one screen-level `role=status` line ("Saving…" / "Saved 10:42" / "Offline, will sync" / "Couldn't save, Retry"), not per-field ticks. `[H]`

## 9. Authentication

- **Passwords** (NIST SP 800-63B-4; GOV.UK; web.dev): allow paste and password managers; no composition rules; min 15 characters if password is the only authenticator, 8 with MFA; accept ≥ 64; blocklist check with an explanation; show/hide toggle (hidden by default, distinct labels per toggle, announce state); no confirm field (raises abandonment); keep the identifier on failure, clear the password; generic failure ("Email or password incorrect"); allow 5-10 attempts before lockout; reset by time-limited single-use link/code, uniform "If an account exists we've sent…" (OWASP); iOS `passwordrules`; `.well-known/change-password`. `[S][P-WEB]`
- **Passkeys/biometrics**: username field `autocomplete="username webauthn"` + `navigator.credentials.get({mediation:'conditional'})` (web) / `performAutoFillAssistedRequests` (iOS) / Credential Manager sheet (Android); keep "Use password" and a recovery path; after a password sign-in try conditional create, else a one-time dismissible "Create a passkey" interstitial plus a settings entry; never block sign-in on enrollment. Prompt moments: account creation, recovery, security settings. Vendor-reported results (X 2× login success, KAYAK ~half auth time, pixiv +29% login success, Dashlane +70% conversion) are directional only. BiometricPrompt for re-auth (BIOMETRIC_STRONG; require confirmation for purchases/health), Credential Manager for sign-in. `[P-WEB][P-iOS][P-AND]`
- **OTP**: one input `one-time-code` + `inputmode=numeric` + `maxlength=N`, auto-submit at length N (keep a button), ≥ 6 digits, single-use, tell users where it was sent and how long it lasts (NIST: valid for at most 10 minutes; GOV.UK uses 15 min, above NIST's ceiling), resend with a cooldown + countdown (30-60 s typical, memory), previous code stays valid until expiry, rate-limit server-side, offer an alternative method; SMS is "restricted" in NIST (prefer WebAuthn). Split boxes: no authoritative evidence; if used, rebuild paste-whole-code, autofill (Android per-position hints), backspace-to-previous and `aria-label="Digit n of N"`, or use one styled input over decorative boxes. `[S][R]`
- **Sign-in options**: allow browsing before sign-in; offer passkey/autofill + "Continue with Apple/Google" + email code. App Store 4.8: if you offer a third-party login for the primary account also offer an equivalent privacy-preserving option; 5.1.1(v) in-app account deletion. Magic links: same-device problems (email app switch, link opened on another device) from memory; time-limit and single-use. Sessions: warn ≥ 20 s before forced logout when you control the timer; on 401 show a re-auth sheet over the form and replay with the same idempotency key (NIST AAL2: 24 h overall / 1 h idle).
- **Accessible authentication (WCAG 3.3.8 AA)**: no cognitive-function tests without an alternative; never block paste; avoid CAPTCHA puzzles. `[S]`

**Money flows (transfers, payments)** `[H]` unless noted: step-up authentication per transfer (BiometricPrompt with explicit confirmation, `[P-AND][P-iOS]`); show amount, fees, rate and total before confirm; defer KYC until the user reaches the first regulated action; cap OTP attempts and resends server-side (NIST allows ≤ 100 consecutive failures; GOV.UK rate-limits after 10 wrong entries) with a visible cooldown; app-unlock biometric opt-in is fine, but don't duplicate the system biometric setting and label it by the real biometry; assume SIM-swap risk, so prefer passkeys or in-app approval over SMS for high-value actions. Android SMS autofill: SMS Retriever (no READ_SMS, 11-char app hash, ~5 min window) or `AutofillHints.oneTimeCode` in Flutter.

## 10. Permissions

Ask on the user's tap of the feature that needs it, optionally one explanation sheet (value in one sentence + a single neutral "Continue"), then fire the system prompt. Purpose string: active voice, specific, one sentence. Never fake "Allow", add Cancel paths, incentives or mimic system dialogs (iOS tracking prompts get rejected). iOS asks once (denial → deep-link to Settings); Android re-askable once with a rationale, second denial is permanent. On denial keep the feature visible with an inline "Enable in Settings" path. Prefer pickers/share sheets/location button over broad access; request approximate over fine location. Never ask at first launch unless the app is useless without it. `[P-iOS][P-AND]`

## 11. Destructive actions

Prefer **undo** for reversible/routine deletes (Raskin 2007: warnings get habituated; NN/g confirmation article): perform immediately + snackbar "Undo" (≥ 10 s, see states-feedback §14; keep a server-side soft-delete window). Confirm only for serious irreversible, bulk or costly actions: dialog titled with the object, verb buttons ("Delete project" / "Keep project"), destructive style on the verb, Cancel always present and not default, name the consequence and scale. Catastrophic (account, workspace): typed name/word + re-auth + timeline (HIG account deletion: schedule option). Don't alert for common undoable actions; destructive style only when the user did not choose the action deliberately; max three alert buttons; never color alone. WCAG 3.3.4 for legal/financial/data: reversible, checked or confirmed. `[R][P-iOS][S]`

## 12. Submit behavior

- Keep the primary button **enabled** when the form has > 2 fields or hidden rules and show errors on press (GOV.UK/Axess Lab: disabled buttons are skipped by AT, exempt from contrast, give no reason). HIG says gate Continue until required data is entered, which is defensible for short guided native steps with visible required cues (OTP of N digits, "Next" after a name): expose why (hint/progress), prefer `aria-disabled`/`accessibilityHint` over `disabled`. Do not use the disabled state for validation gating; while a request is in flight keep the control focusable and ignore repeat taps.
- On submit: ignore re-entrant taps, show an inline spinner on the button and change the label ("Saving…", preserve width), keep it focusable, announce via a polite live region; > 10 s: progress + cancel. Generate an **idempotency key** when the form/payment intent is created and send it with every retry (Stripe pattern: client key, stored result replays the same response, prune ≥ 24 h; the IETF header draft expired). Never rely on disabling alone. `[R]`
- Submit placement: end of the form or a sticky bottom bar; not a top-bar Submit in a long form (NN/g).

## 13. Checklist

Visible labels · single column · fields cut · autocomplete tokens · inputmode/type · enterkeyhint + focus advance · 16px+ web controls · validation timing per field type · specific errors + summary + focus · input preserved · submit enabled + loading + idempotent · destructive = undo/typed confirm · passwords pastable, passkeys offered · OTP single field · permissions in context · keyboard never hides the submit · works at 200% text and with a screen reader.

## 14. Evidence limits

m3.material.io text-field guidance unreachable; HIG text-field and entering-data pages were last updated 2023 and iOS 26 changes are unchecked; split-box OTP, magic links, progressive profiling and resend timers have no authoritative sources; native screen-reader error announcements are from memory; Safari/Firefox `interactive-widget` support unverified; the validation study is 2009 desktop n=22; the Penzo label study is 2006; GOV.UK findings rest on service-team research; thresholds for select-like controls are heuristics; Baymard data is e-commerce-specific; passkey case studies are vendor-reported.
