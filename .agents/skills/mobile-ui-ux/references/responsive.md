# Responsive, adaptive, PWA, foldables and browser-chrome behavior

Read this when: building a responsive or adaptive layout, a PWA/web app on phones, tablet/foldable/landscape behavior, installable web apps, safe areas, keyboard handling in web, viewport units, in-app browsers, Capacitor/Ionic, or deciding breakpoints.

Method: mobile-first → adaptive → responsive. Do NOT scale desktop down or phone up. Design for the smallest window first, then decide per component whether to reflow, reveal, re-architect, or change presentation.

## 1. Vocabulary and the five techniques

Responsive = one fluid layout; adaptive = swap whole layouts at breakpoints. Both Microsoft and Fluent list the same techniques: **reposition, resize, reflow, show/hide, re-architect** (e.g., list/detail). Android: **reflow, reveal, change presentation** (e.g., bottom sheet → side sheet). Rule: grids/cards → responsive (reflow); navigation and list-detail → adaptive (swap bar/rail/drawer, one-pane/two-pane); content that only matters on large screens → reveal (never hide critical tasks; web.dev: don't hide content by screen size alone). `[P-AND][C]`

## 2. Breakpoints and window size classes

- **Content-driven breakpoints beat device breakpoints** (web.dev RWD basics): don't define breakpoints by device/brand/OS; start small and widen until the layout breaks; add a breakpoint when lines exceed ~10 words (70-80 characters). Design systems still publish named tiers for scaffold changes (navigation, panes); component internals use container queries. Android: use window metrics, not device type; confine size logic to the app/content level and pass state down. Microsoft: design for the window, not the screen. `[P-WEB][P-AND]`
- **Material/Android window size classes** (width): compact < 600dp, medium 600-839, expanded 840-1199, large 1200-1599, extra-large ≥ 1600. Height: compact < 480, medium 480-899, expanded ≥ 900. Coverage: 99.96% of phones in portrait are width-compact; 93.73% of tablets in portrait are medium; 97.22% of tablets in landscape are expanded; 99.78% of phones in landscape are height-compact. Classes come from the WINDOW (split-screen, desktop windows, fold state) and change at runtime. Design expanded first then adapt down to medium. Compact height → avoid the top app bar, use horizontal navigation. `[P-AND]`
- **Apple**: size classes compact/regular × width/height, determined by device, window configuration and multitasking state; decide layout by size class, not device or orientation; keep functionality constant, vary content; iPad windows resize fluidly; apps cannot detect or control multitasking configuration. HIG gives no point table. `[P-iOS]`
- Others: Carbon 320/672/1056/1312/1584 px (4/8/16 columns; 16px padding, 32px gutter); Fluent 2 320-479 / 480-639 / 640-1023 / 1024-1365 / 1366-1919 / 1920+; Windows ≤ 640 / 641-1007 / ≥ 1008 epx; Power Apps default [600, 900, 1200]. Default for web `[R]`: scaffold tiers `<600 / 600-839 / 840-1199 / ≥1200` (matches Material), mobile-first `min-width` queries in rem, while content reflows continuously in between. Native Compose: branch on `WindowSizeClass` (width first, then height), never `isTablet`. Large/XL need the adaptive library `currentWindowAdaptiveInfo(supportLargeAndXLargeWidth = true)`.

## 3. Canonical layouts and pane behavior

- **List-detail**: expanded shows both panes; compact/medium one pane at a time, Back returns to the list; state survives configuration changes; `NavigableListDetailPaneScaffold` supports up to 3 panes. **Supporting pane**: expanded 70/30, medium 50/50, compact → sheet or on-demand; supporting content is meaningless alone (else use list-detail). **Feed**: compact single column, medium 2-3 columns, expanded multi-column; `GridCells.Adaptive(minSize=180.dp)`. Apple split views: prefer in regular, not compact, environments; design for narrow/intermediate widths since iPad windows resize fluidly; persistently highlight the selection in each pane. SAP flexible column layout: S single column; M up to 2; L/XL up to 3. `[P-AND][P-iOS]`
- Rule: list + detail AND width ≥ 840dp-equivalent → two panes with highlighted selection; else push navigation with Back; width ≥ 1200 → optional third pane (supporting/inspector); otherwise cap content width instead of stretching.

## 4. Navigation adaptation: bar → rail → drawer/sidebar

`NavigationSuiteScaffold`: compact → bottom bar; medium → bar or rail by orientation; expanded → rail; drawer optional; tabletop posture → bar. Apple: tab bar first on iOS/iPadOS; `sidebarAdaptable` lets the same destinations appear as a tab bar or sidebar; ≤ 5 tabs in the default list; sidebar ≤ 2 levels; never hide/disable tab buttons; avoid "More". Rule: > 5 top-level destinations on phone → consolidate rather than overflow; expanded width → rail/sidebar with labels visible; compact → bottom bar (3-5 items). More in navigation.md.

## 5. Max content width, grids, line length

Android adapt-layout: set max widths on content/components; don't stretch buttons/inputs; grids must change density between sizes (a phone video grid on a tablet is "tight and overwhelming"). Android codelab: max line length 60 characters at expanded; 12-column grid at medium/expanded; 16dp pane padding; 24dp card spacing. web.dev: 70-80 characters. WCAG 1.4.8 (AAA): ≤ 80 characters (40 CJK). Carbon 2x grid: 4/8/16 columns at sm/md/lg+; small has 0 margin and 16px padding. Legacy Material grid: 4 phone / 8 tablet / 12 desktop columns (current M3 margins/gutters per class unverified: compact 4 columns/16dp margin, medium 8-12/24dp, expanded 12/24dp are memory). Rules: text-heavy `max-width: 60-75ch`; forms capped ~560-720px centered on wide screens; cards `grid-template-columns: repeat(auto-fill, minmax(min(100%, 280px), 1fr))` (principle verified via Compose `GridCells.Adaptive`); never go beyond ~1200-1600px content width without adding panes. 8dp baseline (4dp for small elements); Fluent 4px base.

## 6. Fluid type and space, zoom safety

`clamp(min, preferred, max)` for headings, e.g. `font-size: clamp(1.25rem, 1rem + 1.5vw, 2rem)`; keep max ≥ 2× min so text can reach 200% (WCAG 1.4.4); use rem for bounds; body text stays a fixed 1rem; spacing via `clamp()` with rem. WCAG: media-query text changes must still allow 200% enlargement; the "meta viewport allows zoom" test rule. Verify at 200% zoom. Apple: support ≥ 200% via Dynamic Type, rows/containers must grow, text must not crop, adjacent items may stack vertically. `[S][P-iOS]`

## 7. Container queries and intrinsic layout

Components (tables, KPI tiles, cards, list rows) respond to their container (`container-type: inline-size` on the wrapper; switch layout at ~360/480px container widths); page scaffolds respond to the viewport and user preferences. Size container queries are Baseline (Chrome/Edge 105, Firefox 110, Safari 16; widely available Aug 2025: snippet). A container cannot query itself; custom properties can't be used in conditions; style queries not fully supported; media queries still needed for print, orientation and `prefers-*`; grid items shouldn't be containers (wrapper needed). Pajamas uses them in production for table stacking; Compose analogue: `BoxWithConstraints` / adaptive `GridCells`. `[P-WEB]`

## 8. Orientation, multi-window, state preservation

WCAG 1.3.4 (AA): don't restrict to one orientation unless essential (check capture, piano); users mount devices fixed (wheelchairs). PWA: omit manifest `orientation` or use `any`. Android 16: for apps targeting API 36, on displays ≥ sw600dp orientation/resizability/aspect-ratio manifest limits are ignored (games exempt); the opt-out is gone for API 37. Android multi-window is default since Android 12; all visible activities are RESUMED on Android 10+ (don't pause video on ON_PAUSE); handle config changes; set a min size (test at 300×450dp). Fold/unfold restarts the app unless state is persisted (Parcelable/SavedState). Apple multitasking: save/restore context. Rule: hoist state; a form in progress during rotate/resize keeps input and scroll. `[S][P-AND][P-iOS]`

## 9. Foldables and large-screen quality

Size class first, fold awareness as an enhancement. Android `FoldingFeature`: state FLAT/HALF_OPENED, orientation HORIZONTAL/VERTICAL, `occlusionType` NONE/FULL, `isSeparating`; tabletop = HALF_OPENED + HORIZONTAL (content above, controls below); book = HALF_OPENED + VERTICAL; don't put interactive controls or text near an occluding fold. Web: Viewport Segments API Chrome/Edge 138 (`env(viewport-segment-*)`, `horizontal/vertical-viewport-segments` media features); Firefox/Safari none; `device-posture` experimental: keep fold CSS as progressive enhancement behind `@media (horizontal-viewport-segments: 2)`. iPhone Duo (HIG, new 2026-09-09): outer display compact width, inner regular; toolbars/tab bars may move to the side; reserved regions; prefer even column counts; arrangement-view containers; keep navigation containers outside them. Android adaptive quality tiers: Tier 3 (not letterboxed, basic input), Tier 2 (layout optimized for all sizes), Tier 1 (differentiated: multi-window, tabletop/book, drag-drop, stylus). Test configs: foldable 841×701dp, 8" tablet 1024×640dp, 10.5" tablet 1280×800dp, 13" Chromebook 1600×900dp. Add posture handling only for media/camera/reading apps. Surface Duo specifics unverified. `[P-AND][P-iOS][P-WEB]`

## 10. Input modality (touch + pointer + keyboard)

`@media (pointer: coarse)` for sizing and `@media (hover: hover)` for hover effects; use `any-pointer` for progressive enhancement on hybrids (Baseline since Dec 2018). Do NOT infer "phone" from `pointer: coarse` (iPad + keyboard/trackpad, touch laptops). Keep keyboard focus order and visible focus; support mouse, keyboard, stylus and touch equally (Pointer Events); shortcuts as accelerators with visible equivalents. Android quality tiers require keyboard/mouse/trackpad/stylus even at Tier 3. `[P-WEB][P-AND]`

## 11. Desktop-sized viewports for PWAs

Add panes and density, cap widths, switch nav to rail/sidebar; `display_override: ["window-controls-overlay","standalone","browser"]` for desktop PWAs; don't render a stretched phone layout.

## 12. PWA install criteria, UX and manifest

- **Install criteria (Chrome)**: `beforeinstallprompt` fires when: not already installed, user has clicked/tapped at least once and spent ≥ 30 seconds on the page (engagement heuristic; can change), HTTPS, manifest with name or short_name, icons including 192px and 512px, start_url, display in {fullscreen, standalone, minimal-ui, window-controls-overlay}, `prefer_related_applications` absent/false. No service-worker requirement is listed, but ship one for offline. Chrome/Samsung Internet on Android with GMS install a WebAPK; Firefox/Edge/Opera Android create browser-badged shortcuts; Firefox desktop doesn't install PWAs; Safari 17+ macOS "Add to Dock" works with or without a manifest; iOS 16.4+ other browsers can Add to Home Screen via the Share menu; `beforeinstallprompt` not supported on iOS/Safari. `[P-WEB]`
- **Install UX timing**: wait for demonstrated interest; best moments after purchase/sign-up/booking or repeat visits; never the first visit; show the control only after `beforeinstallprompt` fired; keep promotion out of critical flows; always dismissible and remember dismissal; re-prompt only after a relationship change (dismissed → wait 30-90 days is a memory heuristic); `e.preventDefault()` + stash the event, `prompt()` from a user gesture, `userChoice`, `appinstalled`, hide UI when `display-mode: standalone`. On Chromium: an inline "Install app" entry in settings/menu + one contextual banner after the 2nd+ session or a completed task. On iOS (no API): a dismissible instruction card ("Share → Add to Home Screen") only for engaged iOS Safari users not in standalone, never a blocking modal. Google Search: full-page app-install interstitials are intrusive; use small banners or Smart App Banners. Mini-infobar is suppressed by preventing default.
- **Manifest**: `id` explicit and stable; `start_url` deep into the app (not a marketing landing page); `scope`; `display: standalone`; `display_override`; omit `orientation`; `theme_color` (toolbar) + `background_color` (splash, with name + icon) + `<meta name=theme-color media="(prefers-color-scheme: dark)">`; `icons` 192 + 512 + maskable (safe zone = circle of radius 40% of width; separate `maskable` and `any` entries: web.dev's add-manifest page shows a combined `"any maskable"` purpose but the maskable article advises separate icons); `shortcuts`; `screenshots` 320-3840px (Chrome shows up to 8 desktop / 5 mobile; description ≤ 300 characters; richer install UI on Android); `share_target` is Chromium-only and requires an installed PWA (validate input). iOS extras: `apple-touch-icon` (180×180 iPhone, 152/167 iPad), `apple-mobile-web-app-capable`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title`, `apple-touch-startup-image`, `navigator.standalone` (legacy doc; iOS 26 reduces the need).

## 13. iOS PWA constraints (verify current)

iOS/iPadOS 16.4+: web push only for Home Screen web apps (manifest `display` standalone/fullscreen; permission request must follow a user gesture); Badging API; manifest `id` honored. iOS 18.4: declarative web push (no service worker needed; still Home Screen web apps). WebKit ITP (2020 text): script-writable storage (IndexedDB, localStorage, SW registrations/cache) in the Safari browsing context is deleted after 7 days without user interaction; Home Screen web apps are exempt (not re-verified for iOS 26). Safari 26: every site added to the Home Screen opens as a web app by default (user can turn it off; manifest not required but used if present; limits remain: icons/theme/scope/splash customization). EU/DMA episode (Feb-Mar 2024, reversed) from aggregator results only. Rule: if the PWA needs reliable storage or push on iOS → require install (prompt Add to Home Screen) and request notification permission after a user tap; don't promise background sync on iOS; treat Safari-tab data as evictable (sync to the server). iOS 26 Safari reports (one Apple-forum thread, no Apple reply): `position: fixed/sticky` content below the new floating bottom controls isn't rendered: unresolved risk; prefer in-flow bottom bars at page end or standalone-only fixed bars until verified.

## 14. Standalone mode has no browser chrome

`@media (display-mode: standalone|minimal-ui|fullscreen|window-controls-overlay)` (Baseline widely available since Jan 2020). The iOS status bar can't be hidden, only styled (`black-translucent` lets content extend under it). Rule: when `display-mode: standalone` show an in-app header Back where stack depth > 1, a refresh action or pull-to-refresh, a share action, and an "Open in browser" link for external URLs; keep auth/OAuth in a system browser tab/Custom Tab (not embedded); persist scroll and route on app resume. Capacitor Android `backButton` listener disables the default: call `window.history.back()` yourself (`canGoBack`, `exitApp()`); Android 16 predictive back no longer calls `onBackPressed()`.

## 15. Viewport units, safe areas, dynamic toolbars, keyboard

- `svh` (toolbars shown), `lvh` (retracted), `dvh` (tracks changes: not 60 fps, can cause layout shifts; keyboard not counted). `100vh` equals the large viewport so it bleeds past the visible area on load. Chrome 108+/Firefox 101+/Safari 15.4+. Rule: `min-height: 100svh` for content that must always fit; `100dvh` for app shells that should track toolbars (accept jank); never plain `100vh`. `[P-WEB]`
- Safe areas: `viewport-fit=cover` + `env(safe-area-inset-top|right|bottom|left)` (baseline since Jan 2020; `constant()` obsolete; combine with `max()` for landscape padding; always provide fallbacks). Sticky bottom bars get `padding-bottom: env(safe-area-inset-bottom)`. `env()` also exposes `keyboard-inset-*` (VirtualKeyboard API: Chrome Android only, experimental), `titlebar-area-*`, `viewport-segment-*`.
- Keyboard: Chrome 108 made Android Chrome resize only the visual viewport by default (`interactive-widget=resizes-visual`); fixed elements stay and can be covered; `resizes-content` restores the old behavior; `visualViewport` (resize/scroll events, `offsetTop`, `height`) to float bars above the keyboard. Detail in forms.md. Android layout basics: move the focused input up or attach it to the keyboard; don't hide inputs.

## 16. Touch, overscroll, zoom hygiene

`touch-action: manipulation` on controls (removes the ~300 ms double-tap-zoom delay, keeps pinch zoom; `none` can block zoom: accessibility harm). `overscroll-behavior-y: contain` on modals/sheets/inner scrollers (and on `html` only for app-like PWAs that supply their own refresh); stops scroll chaining and, on html/body, native pull-to-refresh/swipe navigation (Safari 16+; not Baseline). `-webkit-tap-highlight-color` is non-standard: if set transparent, supply `:active`/focus feedback. `user-select: none` only where selection is harmful: allow selecting IDs and amounts. Never `user-scalable=no`/`maximum-scale=1` (WCAG 1.4.4; iOS 10+ ignores it by default). `[P-WEB][S]`

## 17. Service-worker update UX and offline page

New SW waits until the old controls zero clients; `skipWaiting()` can leave pages loaded with old assets handled by the new SW (mismatch risk). Workbox prompt flow: `workbox-window` `waiting` event → "update available" UI → `messageSkipWaiting()` → `controlling` → reload. Rule: show a non-blocking snackbar "New version available: Reload" (persist until chosen; never auto-reload mid-form/draft; apply on next navigation or idle; defer if the form is dirty). Ship a branded `/offline.html` precached at install with a retry button and the list of available cached sections (Workbox `setCatchHandler`/`offlineFallback()`). Strategies and offline UX: performance.md and states-feedback.md.

## 18. In-app browsers and webviews (Instagram, Facebook, TikTok, LINE)

In-app browsers lack extensions/downloads/bookmarks, can inject JS and observe input, don't share logins/history, and may be outdated. localStorage may be cleared on navigation in some webviews (snippet): use cookies/sessionStorage and a server session. PWA install is unavailable. Google blocks OAuth in embedded webviews (`disallowed_useragent`; Android UA contains `; wv`) since 2021 (Auth0 summary). Some cross-document view transitions failed in Facebook/Instagram Android webviews (GitHub issue). Android: WebView has no navigation controls or address bar; use Custom Tabs for external content; never allow navigation to untrusted sites in a WebView with JS bridges. Rule: detect (UA heuristics + feature checks) and show a dismissible banner "Open in Safari/Chrome for the best experience" with a copy-link fallback before login/checkout/install; use redirect-based OAuth in the system browser; skip view transitions and install prompts there.

## 19. Capacitor/Ionic and TWA (high level)

Capacitor Status Bar: `overlaysWebView` default true; on Android 16 (API 36) overlay/background options are unsupported because edge-to-edge is enforced; on Android WebView with edge-to-edge `env(safe-area-inset-*)` can be 0 (community reports; fixes: Capacitor `adjustMarginsForEdgeToEdge`, safe-area/SystemBars plugins). Rule: set both CSS safe-area padding and native inset handling; test the status bar/nav bar on Android 15/16 and iOS; handle the back button; use a real browser (Custom Tab/SFSafariViewController) for external/OAuth links. TWA: runs the web app in Chrome (not WebView), needs Digital Asset Links, Chrome 72+, Bubblewrap/PWABuilder; host app can't read cookies/localStorage; the Chrome TWA page fetched looked stale (check current docs).

## 20. Landscape, keyboard, small heights

Compact height (< 480dp; 99.78% of phones in landscape) → collapse the app bar/bottom bar on scroll, move the primary action into content, avoid sticky stacks (top bar + chip row + bottom bar) leaving < 50% of the height for content; test with the keyboard open in landscape. WCAG 1.4.10: content must work at 320 CSS px wide (vertical scroll) and 256 px high (horizontal scroll). NN/g: don't force landscape for tables. `[S][P-AND]`

## 21. Anti-patterns

Desktop UI scaled down or phone UI scaled up; device-type checks (`isTablet`) instead of window size; fixed-pixel layouts; `100vh` for full-height shells; orientation locks; disabling zoom; hover-only controls; blocking install popups on first visit; full-page app-install interstitials; PWA without in-app Back in standalone mode; fixed bottom bars with no safe-area padding; stretching full-width buttons/inputs on tablets; relying on Background Sync on iOS; auto-reload on SW update mid-form.
