## 3. LEAKS (stated universally, actually platform-specific)

1. Rule 63 and rule 67 (INP) are tagged `[P-WEB]`. Rule 1 ("reachable bottom edge or sticky footer, ≥ 48dp") mixes dp into a universal rule. Rule 22 gives three units but no instruction to choose by stack.
2. Rule 80, "off-black canvas, `#121212`, lighter surfaces for elevation", is Material 2/3 dark theory. iOS uses true-black base plus raised grays, and Apple's own system background is `#000`. SKILL.md §8 presents `#121212` as the default for any stack. Needs `[P-AND]`/`[C]` labelling and an iOS exception.
3. SKILL.md §8 "Defaults ... radius 0/4/8/12/16/28/full" is the M3 scale (design-tokens.md:82). `[R]` over-states a Material-specific preset. Use `[C]` and say it is Material-derived.
4. Rule 36 and the carousel guidance are web/NN/g. Rule 56 "snackbar" is Material vocabulary. iOS has no snackbar, and HIG discourages timed UI (accessibility.md:93). The universal term should be "transient confirmation", with iOS using an inline state, an undo shake or a toast-style banner.
5. Rule 11 "persistent bottom bar" for 3-5 destinations and rule 12 "rail" are Material window-class idioms. iOS 26/iPadOS use a tab bar that becomes a sidebar. Rule 12 is not wrong, but rule 11's `[P][R]` should say which platform.
6. Rule 15 "register back properly on Android" is correct but there is no iOS equivalent (edge swipe, nav stack). Back is called "predictable", yet iOS has no system Back button. The rule is Android-centric.
7. Rule 73 "spring bounce 0 default" derives from Compose/SwiftUI spring terminology. It is not meaningful on CSS (no native spring until `linear()` easing).
8. Rule 113 "sentence case cross-platform; title case only in native iOS chrome". Material is sentence case, and Apple HIG uses title case for buttons and nav titles. Calling this `[C]` hides that it is a platform split.
9. Rule 58/59 (optimistic UI, offline queue) are architecture decisions the skill treats as UX defaults. Offline-first is not a universal default (see MISSING).
10. Rule 46 permissions: "ask in context on the user's tap". iOS permits one system prompt per permission, so a pre-prompt priming screen is essential there. On Android 11+ the same applies after two denials. The rule needs the platform branch.

## 4. WEAK RULES AND REWRITES (25)

Numbers refer to decision-rules.md.

1. **#10** "ask or state an assumption" has no tag or threshold. Rewrite: "IF primary goal or user role is not stated THEN write a one-line assumption at the top of the reply and proceed. Ask only when two plausible readings lead to different navigation structure."
2. **#4** "structure them instead of cutting or capping" `[R]`. This is weak evidence (Baymard assortment). Rewrite: "IF a choice set exceeds ~7 THEN group, sort, filter or search before cutting. Cut only options nobody uses (check analytics) `[H]`."
3. **#5** "IF desktop info cannot fit THEN redesign" has no threshold. Rewrite: "IF a screen has more than one column of content or more than 5 table columns THEN produce the task table first, then redesign `[H]`."
4. **#6** feedback "≤ ~100 ms" is `[R][P]`. Rewrite: "IF an interaction changes state THEN show a pressed or in-progress state in the next frame, and never later than 100 ms `[R: Nielsen limits]`."
5. **#19** "> 2 levels of navigation visible at once" `[H]` has no reason. Rewrite: "IF more than two levels of navigation are visible at once on a phone THEN flatten (a bar plus one tab strip is the maximum), because chrome height is lost to content `[H]`."
6. **#53** has no row for known-duration or determinate-eligible tasks. Rewrite: "IF the duration is measurable (upload, export, install) THEN show determinate progress from the start, even under 10 s. IF unknown THEN use the 1-10 s ladder."
7. **#54** is a `[H]` stated as a tight number. Rewrite: "IF a loader would flash for under ~300 ms THEN delay it 200-300 ms and hold it ≥ 400 ms once shown. Platform libraries differ (AndroidX 500/500) `[H]`."
8. **#56** hides the distinction. Rewrite: "IF a result is routine and visible elsewhere THEN a transient confirmation (4-6 s `[H]`, honoring system timeout settings). IF it carries an error, Undo as the only recovery, or user action THEN persistent. On iOS use inline state or a banner, not a snackbar."
9. **#58** "cheap reversible actions" is undefined. Rewrite: "IF the action is reversible within the app, has a high success rate (>95% `[H]`) and a visible rollback THEN optimistic. Never for payments, sending messages to others, or deletions without soft delete."
10. **#59** "IF offline THEN cached reads..." is stated as a requirement for all apps. Rewrite: "IF the product has field or low-connectivity use THEN offline reads and queued writes. Otherwise show a clear offline state and block writes, and say which scope you chose."
11. **#27** "never thumb-zone-only" is a negative. Rewrite: "IF a flow is one-handed-critical THEN put the primary action in the lower half and give an alternative top-of-screen path. Do not rely on thumb-zone maps `[H]`."
12. **#30** "≤ ~3 inputs" is a bare number. Rewrite: "IF a task needs ≤ 3 inputs and no navigation THEN a sheet. IF it needs scrolling or branching THEN a full page. Threshold is `[H]`."
13. **#33** thresholds with no tag order. Rewrite: "IF 2-4 options THEN radios; 5-10 THEN picker; 11-15 THEN sectioned picker; >15 THEN searchable. All cut-offs are `[H]` (forms.md §7); never present them as a standard."
14. **#35** "Load more (15-30/batch)" vs data-dense's 25-50. Rewrite: "IF task lists are long THEN Load more with a count; batch 15-30 on phones, up to 50 for dense admin lists `[H]`."
15. **#38** "cut/defer first/last name split ... promo code" is over-specific and culturally brittle. Rewrite: "IF a field has no immediate use THEN cut or defer it. Prefer a single full-name field unless the downstream system needs parts (names are not universally two parts) `[R]`."
16. **#42** "idempotency key" mixes UX and backend. Rewrite: "IF a submit mutates server state THEN disable duplicate taps in-flight and send an idempotency key (backend requirement)."
17. **#48** "prefer in-flow submit; else sticky..." is vague. Rewrite: "IF the form fits on one screen with the keyboard open THEN in-flow submit. IF it scrolls THEN a sticky footer inside the scroll container with IME inset and safe-area padding."
18. **#64** "≤ 1-2 small static chrome surfaces" `[R][H]` has no source. Rewrite: "IF blur or translucency is requested THEN limit to one static bar, provide an opaque fallback for Reduce Transparency, and measure on a mid-tier device `[H]`."
19. **#66** web JS budget "300-600 KiB" is `[H]` but presented as an actionable number. Rewrite: "IF no budget is given THEN agree one and measure LCP, INP and CLS on a mid-tier Android device on slow 4G. 300-600 KiB compressed JS is a starting guess `[H]`."
20. **#71** `[S]` is wrong for ms numbers. Rewrite: "feedback ~100 ms, partial surfaces 200-300 ms, full-screen ≤ 400 ms, never > 500 ms `[H]`, synthesised from NN/g and Material."
21. **#74** stagger "≤ 20 ms/item" `[S]` is a Material 1 number. Rewrite with `[H]` and "default to no stagger in utility apps".
22. **#81** "inner radius = outer − padding" `[P]` is an Apple/Material nesting rule. Rewrite: `[C]` for web or custom stacks.
23. **#104** "3-5 KPI tiles" `[R][H]`. SKILL.md itself calls it a heuristic. Rewrite: "IF a dashboard THEN lead with what needs attention, then the fewest KPIs that answer the user's question (start at 3-5 `[H]`)."
24. **#106** "different task-first IA per role" `[H]`. Rewrite: "IF roles have different top tasks THEN give each its own home and destinations. Do not hide the other role's features behind permissions with no explanation."
25. **#114** is an instruction with no gate on how to offer the variant. Rewrite: "IF a request asks for a dark pattern THEN decline that element, say why in one sentence, and ship the honest variant (e.g. true deadline, balanced accept/reject)."

## 5. MISSING RULES (an agent would still guess)

- **PWA vs store vs native decision.** Proposed: "IF the app needs background sync, reliable push on iOS, deep OS integration (NFC, Bluetooth, widgets) or store distribution THEN native or hybrid. IF content-led, link-shared or updated often THEN responsive web or PWA. State the choice and the loss. `[H]`" responsive.md covers PWA mechanics but not whether to build one.
- **Offline-first scope.** Proposed: "Choose one level and state it: (0) online only with a clear offline state; (1) cached reads; (2) queued writes; (3) full sync with conflict resolution. Default 1. Level 3 needs a conflict rule (last-write, merge, ask the user)." data-dense.md §14 is the only mention.
- **RTL and bidi.** ux-writing.md:70 has the HIG guidance only. Proposed: "Use logical properties (start/end, `margin-inline`), mirror directional icons, not media controls or numerals, test with real Arabic or Hebrew strings, and never concatenate strings."
- **Push notification UX.** states-feedback.md §17 covers permission timing and content. Missing: channels and categories, quiet hours, frequency caps, a deep link on every notification, a settings screen that lists each type. Proposed: "Every push has a user-benefit reason, a deep link and a mute path in settings."
- **Tablets and iPad.** responsive.md gives window classes but no guidance on iPad multitasking, keyboards or pointers. Proposed: "On ≥ 840 dp: two-pane, sidebar, constrained text width. Support keyboard shortcuts and pointer hover for iPad and desktop PWAs."
- **Number, date, currency and unit formatting beyond `Intl`.** data-dense.md:94 only. Proposed: "Never format by string concatenation. Show currency code when the account is multi-currency. Use the locale's decimal separator in input and parse it. Right-align numerals in columns."
- **Authentication session policy.** Missing: session timeout, biometric re-auth for sensitive actions, and logout on shared devices.
- **Onboarding.** components.md §9 and ux-writing.md mention it. No rule on skippable tours or first-run value. Proposed: "Show value before sign-up; cut tours longer than 3 screens; teach in context."
- **Rating and review prompts** exist only in a mention. Add timing (after a success moment, never after an error), once per version, and honoring platform limits.
- **Image and media.** Missing: aspect-ratio rules, alt text for user content, captions, autoplay and sound defaults, and data-saver mode.
- **Low-bandwidth and low-end devices.** performance.md names a mid-tier target but not data saver, offline images or reduced animations on low-end hardware.
- **Error budgets and permissions.** Missing: handling "ask every time" location permission (iOS 14+ approximate location) and Android photo picker.
- **Content users cannot control.** Long names, emoji, mixed scripts, user-generated images, truncation policy (middle vs end truncation for IDs and filenames).
- **Privacy and consent UI.** Only cookie banner asymmetry is covered. Missing App Tracking Transparency, data deletion path (store requirement), and analytics opt-out.
- **Haptics, sound and voice.** Rule 76 only. No voice-input or dictation guidance.
- **Older users, children, low literacy.** No age-inclusive guidance beyond WCAG; add larger default targets and plain-language reading level for public-service apps.
- **App-wide search and filtering behaviour** is covered, but empty-result recovery for typo and synonym is not.

## 6. BIAS (trend-like or house-style defaults)

- **Bottom navigation as the default for 3-5 destinations**, and an assertion that the hamburger is "retired" (product-patterns C1). Evidence is a platform convention plus one NN/g study. The "Strong" rating is a cross-product observation, not a test result.
- **M3-shaped tokens as universal defaults**: radius 0/4/8/12/16/28, state layers .08/.10/.10/.16, `#121212` canvas, duration tokens named after M3 short/medium. The skill never says "this is Material-derived", so iOS-first or brand-led products inherit Android conventions.
- **Anti-trend stance as a trend.** SKILL.md §1 and rules 9, 84 bar gradients, glass and large radius, and rule 98 allows glass only for the "functional layer". The review-system treats these as defects even though iOS 26 ships Liquid Glass. The skill is honest in tagging `[T]` but rule 84 ("remove it") is a house taste.
- **Sentence case** across platforms (rule 113) is a Google/GOV.UK preference.
- **Enterprise bias.** Worked example, school/ERP/CRM patterns and "do not import consumer patterns" (rule 107) push toward utility UIs. Consumer products where engagement is legitimate (games, media, social) are given little help. Rule 107 reads as universal.
- **Western-centric defaults.** Name fields, address order, date formats, "Step n of N" and left-to-right icon direction. RTL appears only in ux-writing.
- **Reduce-first.** Principle 12 and rules 3-5 favour fewer and simpler features. Some domains (pro tools, trading, maps) need density.
- **"Undo over confirm" as the default** (principle 5, rule 45) comes from the Raskin and Gmail example. It assumes soft delete exists, which many backends lack.

## 7. HONESTY

- **Tags that overclaim.** Rule 71 `[S]` (ms numbers), rule 74 `[S]`, rule 72 `[S]`, rule 75 `[S][P]` (150 ms), rule 61 `[R]` for the transform/opacity rule (that is `[P-WEB]`), rule 79 `[R]` for the default token set (it is `[C]`/`[H]`), rule 84 `[H]` (fine), rule 105 `[S][C]` (tabular figures are a convention), rule 60 `[S 1.4.1]` (the icon + label part is `[C]`).
- **Rules with `[R]` whose sources are heuristics or single sites.** Rule 4, 5, 47, 49 (3-6 fields per step), 101, 103. The skill itself says forms.md §7 thresholds are heuristics, but rule 33 is tagged `[R][H]` and reads as fact.
- **SKILL.md §1** says the rules "come from primary sources ... cross-checked and tagged". Yet 79 `[H]` uses exist, m3.material.io was unreachable (SKILL.md §9 admits it), and many M3 numbers are "memory". The headline should say "partly from memory" near the first claim, not only in §9.
- **Undefined tags** (`[D]`, `[O]`, `[R-weak]`, `[R-T2]`) mean a reader cannot decode the evidence class. `[D]` is used for the 0.7x exit factor, which is derived, not sourced.
- **Contradiction between honesty and certainty.** Rule 117 says to tag unsourced claims `[H]`, but SKILL.md §5 shows the 40-rule digest with no tags at all. A user reading only SKILL.md sees heuristics as facts. Add tags or a one-line note "numbers here are defaults, see tags in decision-rules".
- **Research date 2026-10-06** and "iOS 26 / Android 16 / API 36-37" claims are volatile (rule 97, 98). Flagged in rule 119, but stated in rules without `(verify)`.
- **Evidence-limits sections** exist in each file. This is good and uncommon. The gap is that none is summarised in SKILL.md.
